# AGENTS.md

- Proposal slide images live in the private `propostas-slides` bucket (workspace blocks public buckets); `conteudo.apresentacao.slides` stores public-format URLs and the public page swaps them for signed URLs server-side, always looked up by token.
- Proposal visits (`proposta_visitas`) are written only by server functions in `propostas-publico.functions.ts` with the service role; one row per browser session, and preview (`?previa=1`, `?imprimir=1` or a signed-in Compass user) records nothing.
- Proposal alert e-mails (`src/lib/propostas/avisos-email*.ts`) go through the same Resend connector as the other Compass e-mails, to `propostas.avisos_emails` (empty → the sender's profile e-mail); they never throw, every attempt is logged in `integration_logs` (action `proposta_aviso_email`), `PROPOSTA_AVISOS_EMAIL_SIMULAR=1` skips the real send, and a signed-in Compass caller (preview) gets no e-mail.
- Site forms enter through `POST /api/public/mkt/conversao` (rules in `src/lib/mkt/conversao.ts`, writes in `conversao.server.ts`, service role only): the asset's public `chave` authenticates, every submit is a new immutable `mkt_conversoes` row, and the SDR card is created/updated in `leads` with the lead/contact spine linked by the existing `leads_vincula` trigger.
- `leads.sem_ia_automatica` (copied from `mkt_ativos.sem_ia_automatica`) must be honored by every automatic WhatsApp sender for new leads: AI opening, `new_lead`/`stage_change`/`no_reply` rules and FUP sequences; routing and the human SDR cadence still apply.
- New users: `createUser` sends no e-mail; the super admin edits and sends the welcome e-mail right after (or later via "Boas-vindas" in Usuários) through `sendWelcomeEmail` (draft/HTML in `src/lib/boas-vindas.ts`, Resend, logged in `integration_logs` action `boas_vindas_email`). It links to the public manual at `/manual` (`src/content/manual-compass.html`, served without login by `src/routes/manual.ts`).
- Usage logs: `useRegistroDeUso` (in the `_app` shell) records each tab session, page opened and a 5-minute "active" ping (only with the tab visible and recent interaction) into `uso_eventos` via `registrarUso` (service role; RLS on, no policies). Only the e-mails in `ACESSO_LOGS_USO` (`src/lib/uso.ts`, today just talita.sigales@grougp.com.br) can read them, at `/uso` (summaries come from the `uso_resumo`/`uso_telas`/`uso_ultimo_acesso` SQL functions, service role only). Events before the app started logging (from 23/11/2026) were reconstructed from login refreshes and recorded CRM actions, flagged `reconstruido = true` (tipos `aberto`/`acao`, deduped by `origem_id`); `aberto` never counts as active time.
